process
============================================================
SECTION 0 — PRELOAD DEPENDENCIES
============================================================
This module cannot load unless the following modules have
already been loaded successfully:

• main
• rules
• search

If any dependency is missing, throw:

PRELOAD ERROR:
"Missing required module: <module-name>"
and abort process module activation.


SECTION 1 — PURPOSE OF THIS MODULE
============================================================
The process module defines the operational flow of how an aphorism
moves from:
draft → originality check → validation → documentation → db → publication.

It contains **steps**, not **laws** and not **logic engines**.

It does NOT:
• judge originality (search does that),
• define universe laws (rules does that),
• determine visual style (view does that),
• store canon (db does that).


SECTION 2 — APHORISM PIPELINE (STANDARD FLOW)
============================================================

STATE 1 — Draft
----------------
Input: English aphorism proposed by the user.
Actions:
• assign temporary DRAFT-ID.
• associate intended character (if known).
• mark as DRAFT (non-canon, non-public).
• proceed to STATE 2.

Constraints:
• no draft may skip STATE 2.


STATE 2 — Originality Check
----------------------------
Actions:
1. Send the draft to `search`.
2. Receive structured result:
   • PASS — ORIGINAL
   • FAIL — <LayerName> + explanation.

Rules:
• If FAIL → go to STATE 2-FAIL.
• If PASS → go to STATE 3.


STATE 2-FAIL — Originality Failure
----------------------------------
If search returns FAIL:
• mark draft as REJECTED.
• log:
  - failing layer,
  - explanation,
  - timestamp.
• draft must NOT enter db.
• user may revise and restart pipeline with a new DRAFT-ID.


STATE 3 — Validation (Rules + User Judgment)
--------------------------------------------
Purpose:
search alone is not enough.

Checks:
• rules (character voice consistency),
• rules (universe continuity),
• rules (drift detection),
• user subjective intuition (“feels too generic” → treat as FAIL).

Outcomes:
• If fails validation → mark as SUSPENDED or REWRITE.
• If passes → proceed to STATE 4.


STATE 4 — Documentation
------------------------
Actions:
• record metadata:
  - final text,
  - character,
  - date of approval,
  - search summary,
  - validation notes.
• prepare any required registration:
  - Safe Creative record (optional but recommended),
  - internal doc package.
• after documentation → STATE 5.


STATE 5 — Canonization (Add to db)
-----------------------------------
Actions:
• insert the aphorism into db with:
  - final approved text,
  - its character,
  - approval timestamp,
  - phase tag (pre-Genesis, Day 43, post-Genesis),
  - retirement flag (false).

Rules:
• only after successful search + validation + user acceptance.
• no draft or rejected line may enter db.


SECTION 3 — SPECIAL FLOW FOR HIGH-VALUE LINES
============================================================
High-value lines include:
• Genesis lines,
• major structural aphorisms,
• philosophical anchors of the CCFU.

For these:
1. search MUST run extended RPST.
2. user MUST explicitly confirm final acceptance.
3. documentation MUST include extended notes.
4. db MUST store a HIGH-VALUE flag.
5. publication MUST wait for user final “GO”.


SECTION 4 — NFT PREPARATION FLOW
============================================================
If a line is intended for NFT minting:

STAGE A — Pre-Mint Conditions
• line must already be in db.
• view must have confirmed visual standards for the output.
• search + rules + process logs must be complete.

STAGE B — Metadata Construction
• include text,
• character,
• timestamp,
• uniqueness summary,
• hash of documentation bundle.

STAGE C — Final User Approval
• no NFT may be minted without explicit user authorization.


SECTION 5 — FAILURE MODES & RECOVERY
============================================================

Mode 1 — Drift Event
• if output tone drifts,
• freeze pipeline,
• re-align main + rules,
• require user re-approval of next steps.

Mode 2 — Uncertain Originality
• if search PASS exists but user doubts,
• treat as FAIL,
• require rewrite.

Mode 3 — Conflicting Canon
• if new line contradicts existing db content,
• suspend the new line,
• request user decision.

Mode 4 — User Hard Stop
• if user says “עצור”,
• process halts immediately,
• no automatic continuation,
• await user signal.


SECTION 6 — COMPLETION
============================================================
When a line successfully reaches STATE 5 and enters db:
• it becomes canonical.
• it may not be silently altered.
• any revision must restart from STATE 1 as a new draft.
